# 前端重构前阶段审查

日期：2026-09-12。审查代码基线：`cf43ab5`，分支 `codex/inventory-merge-recovery`。

## 结论

核心主流程已形成，现有全部回归通过；补充审查发现 4 项应在前端重构前解决的问题、2 项业务/校验边界，以及 1 项错误态展示问题。当前不标记“后端冻结”或“生产就绪”。可以开始前端信息架构规划，涉及数量、取消恢复和历史的页面先等待规则补齐。

本轮只做审查、独立环境测试与文档整理，未修改业务实现、数据库结构、依赖或用户验收数据。结构重组和缺陷修复待确认后分批执行。

## 前端重构前应解决

| 编号 | 复现场景与实际结果 | 影响与建议 |
|---|---|---|
| G1 | 保存菜单时库存单位 kg，预计量填 1；将库存改为 3000 g 后再打开核对，页面显示实际用量 1 g，确定按钮可用，没有单位变化提示 | 原预计量含义丢失。备餐保存预计量单位快照；单位变化后明确换算或要求重新填写，不能静默沿用数值。需要数据模型、迁移与契约调整 |
| G2 | 有正式消耗的餐撤销后取消，同日期餐次新建返回 409；编辑已取消记录返回 409；删除因历史引用返回 409 | 此餐次没有可行恢复路径。建议恢复原记录为待完成，保留历史和“一餐一条”。这项是产品取舍，已发选项确认 |
| G3 | 同一食材用于两道菜，分别用 1、2；整餐合并恢复总量 3 正确，但两条审计恢复量分别为 0、3 | 库存总数正确，按菜历史归属错误。当前代码拿库存前后快照差当每道菜恢复量，而确认只在最后一项写合计扣减。应按每项实际量记录，并处理分数汇总舍入尾差 |
| G4 | 原 stock_text=2、stock_value=2；PATCH 只提交 stock_value=5 和最新版本，200 返回 stock_text=2、stock_value=5 | API 可产生“展示 2、实际计算 5”的不一致。应明确数量字段成组更新/校验或由后端生成配套展示值，继续保留合法数量原文 |

证据入口：

- G1：`daily_battle_preparations` 只有 `planned_quantity_text`；[备餐读取/保存](../backend/app/menu_workflow.py)、[核对初始化](../frontend/src/MenuWorkflow.tsx) 按当前库存单位解释旧文本。3050 菜单 ID 10 的浏览器已实证“1 kg → 1 g”。该问题发生在打开核对窗口之前改单位；打开窗口之后改单位已有阻拦，不能用后者的通过证明前者安全。
- G2：[餐次唯一、取消、编辑、删除](../backend/app/routes/daily_battles.py)。保留历史是正确规则，不能通过删除历史绕过。
- G3：[按整餐汇总扣减](../backend/app/routes/daily_battles.py) 与 [恢复审计写入](../backend/app/recovery.py)。补充脚本直接读出 used=1/restored=0、used=2/restored=3。
- G4：[库存 PATCH](../backend/app/routes/ingredients.py) 独立处理 stock_text/value/unit，生成类型也允许各自可选。

## 需要明确或随前端重构处理

| 编号 | 已观察到的事实 | 建议 |
|---|---|---|
| G5 | 菜品已经用于待完成菜单但未被搭配引用时，删除菜品返回 200；随后原样编辑该菜单返回 404。直接确认仍可依靠已复制的快照，因此不是所有路径都失效 | 在“待完成菜单引用时暂不允许删”和“允许删，但已有菜单照常按快照编辑”之间选择；推荐前者，已发选项 |
| G6 | 预计量填“随便写”可以保存；后端只检查非空，实际量填合法数字后可确认。前端不能将该预计量默认带入数字输入 | 明确预计量是自由文本还是合法数字/分数。推荐库存耗材非空时校验数字/分数，空白仍允许保存草稿；若保留“适量”，应明确要求核对时另填实际量。这项不能只根据现有代码认定业务已确认 |
| G7 | 模拟断网后点击“冰箱冷藏”，页面同时显示“暂时连接不上厨房”和“没有找到这些食材”；恢复网络切回全部可继续使用 | 前端分别呈现 loading/error/empty/success；错误态提供重试，不把读取失败解释为空库存 |

其他 UX 观察：库存不足提示在弹窗顶部和食材行重复；已有库存只是不足时仍提示“将待购买食材关联到库存”，应按问题类型给引导。后端永久不可撤销与可刷新版本冲突应区别提示，不能都让用户不断刷新。

## 技术栈和代码设计建议

保留 React 19 + TypeScript + Vite、Python 3.13 + FastAPI + asyncpg、PostgreSQL。当前问题来自规则衔接和实现组织，没有证据表明需要换框架、引入微服务或缓存中间件。

| 优先级 | 调整 | 为什么 |
|---|---|---|
| 重构前 | 先修 G1–G4，确认 G2/G5 取舍，明确 G6 | 避免新前端继续围绕错误语义开发 |
| 重构前 | 把失败复现转为精确的行为测试；补成功响应 schema 校验、单位变化和历史归属断言 | 现有测试只检查了整餐总量和“存在审计”，漏掉每条审计恢复量；类型生成不能验证业务 |
| 随前端重构 | 按库存、菜单、菜品/搭配拆组件和状态；请求、领域计算、弹窗分层 | App.tsx 1464 行、App.css 1599 行，集中处理多个模块；便于针对一个模块改动和验证 |
| 随后端修复 | 整理库存路由的压缩多语句写法；单位换算规则集中到单一后端模块并用测试约束前端 | 同一换算表存在于库存路由、恢复模块和前端多个位置，容易再次漂移 |
| 分步推进 | 用已有 Pydantic 定义请求与响应模型，逐步替代手写校验 + 人工 api_contract 双份字段；保持现有 API 名称和错误外形 | 缩小文档与运行校验分离的范围；不一次性重写所有路由 |
| 重构前安排 | 一条统一阶段测试命令，按场景创建独立库并汇总失败；独立前端端口/代码目录 | 目前测试固定日期、启动顺序和日志靠手工管理，容易遗漏；仅换端口不隔离热重载代码 |
| 可后置 | 分页按页面加载、局部刷新；错误追踪和请求关联 ID；FastAPI lifespan 替换旧事件写法 | 主页面当前一次读取五类全量列表，规模增大后再测量优化；保持本轮无依赖升级 |

建议依据：FastAPI 官方支持按模块组织 [APIRouter](https://fastapi.tiangolo.com/tutorial/bigger-applications/)，也支持由 [Pydantic 请求模型](https://fastapi.tiangolo.com/tutorial/body/) 同时提供校验和文档；React 官方建议避免冗余、矛盾和重复的 [状态结构](https://react.dev/learn/choosing-the-state-structure)。具体拆分粒度是本项目判断，不是“官方规定必须采用某套目录”。
