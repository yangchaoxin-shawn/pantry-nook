## 本轮处理

| 用户反馈 | 落实结果 |
|---|---|
| 位置可不填，但应提醒补全 | 待补位置标记、全库存计数与筛选，点击直达位置字段 |
| 数量滚动精度过细 | 明确 ±1 控件，手动小数保留；聚焦才响应滚轮；批量手机行分层排布 |
| 仅改单位无法保存 | 按需成组发送数量原文、值、单位；数量不变可保存属性修改，分数原文保留 |
| 子页没有归属与返回 | 处理记录、常用搭配加入父级路径及返回；恢复父页搜索、筛选、滚动位置 |
| 菜品布局与手机按钮比例 | 连续手写菜品簿，按菜名长度自然排列；手绘标记、完整换行与 6:4 编辑/删除区域 |
| 核对仍显示旧库存、补货后走丢 | 首开/返回/前台定时重读；同一餐内补货、明确关联、继续核对；实际量草稿保留 |
| 历史及新餐安排缺少时间感 | 日期时间线与同日餐次分组，待完成/历史分区，保留筛选、展开记录及全部原操作 |

额外修复本次流程暴露的边界：同数字重填新单位、菜单并发修改叠加库存换单位、入库成功后关联失败不再重复入库、未知结果按实际提交名称核对。

## 实际验证

- 7 个相关前端测试文件合计 **67 项**通过，覆盖库存编辑、数量步进、库存视图、批量录入、菜单核对、草稿/单位与时间线；不是全量测试。库存等 5 文件输出 51 项，最终菜单两文件输出 33 项（其中菜单核对 20 项与前批重合），时间线 3 项。
- `npm.cmd run typecheck`、`npm.cmd run lint`、`npm.cmd run build` 通过，最终 build 包含最终代码的 TypeScript 检查。未升级依赖。
- 浏览器真实 API：燕麦补位置后仍显示 `1/2kg`；南瓜只改单位成功；手填 `0.25` 后增加 1 得到 `1.25`。
- 浏览器导航：库存搜索“南瓜”往返处理记录、菜品搜索“番茄”往返常用搭配，搜索保留；父级路径与返回入口可见。
- 排骨待购流程：鸡蛋实际填 `0.75` → 取消补货保留 → 排骨入库 `1kg` → 明确关联并填预计 `0.5kg` → 回到原餐仍保留鸡蛋 `0.75` → 确认后进入当天历史。API 核实排骨剩 `0.5kg`、鸡蛋剩 `7.25个`。
- 同 ID 补量：胡萝卜库存 `3→5个`，返回核对实际 `4个`、鸡蛋 `0.5个`均保留。模拟本标签断网时禁止确认，重连自动恢复且输入保留；网络模拟已还原。
- 菜单并发与单位：A 保留原 `0.3kg`，B 改菜单为 `100g`、库存改为 g；A 保存先显示冲突，核对后显示 `0.3kg→300g`，再次保存才写入。西兰花单位从个改 kg 后重填数字 1，API 核实保存为 `1kg`。
- 时间线：已完成餐归入当天历史；展开消耗记录可达；日期筛选有结果、无结果与清除筛选均通过。

## 用户重点验收

1. 菜品簿的自由排布与手写节奏是否符合“大胆设计”，手机编辑/删除是否顺手。
2. 库存直接补位置、只改单位、数量增减是否符合日常操作。
3. 从核对补货再回到同一餐是否顺畅；日期时间线是否更易找餐记录。
