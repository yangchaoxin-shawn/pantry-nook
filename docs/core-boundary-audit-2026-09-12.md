## 下一轮优先事项

1. **异常恢复引导**：当前撤销遇到同名新库存会安全拒绝，但没有将旧记录与新库存合并的业务操作。建议先保持安全拒绝，体验迭代增加明确的库存定位入口；若要合并撤销，需要另定单位、数量、历史归属和重复撤销规则。
2. **库存为零的语义**：当前批量录入允许 0，编辑库存不允许直接改为 0，耗尽/全量报废会移出在库列表。建议下轮明确“未买到的食材只属于餐安排待购买，入库必须大于 0”，确认后统一 API 和表单；本轮不自行改变已接受的录入范围。
3. **双人编辑非数量字段**：菜单、库存数量有版本保护；菜名、搭配、库存备注等尚未全面要求编辑版本。不会因此重复扣库存，但同一字段可能后写覆盖。建议下一轮统一编辑冲突提示，避免每个模块自行解释。

这些是边界/体验待决项，不是新增购物、统计或角色模块的实施授权。先做上述小迭代，再进行完整 UI/UX 重构，重构继续遵循同一业务契约。

## 上线门槛（本轮未实施）

- 无登录不等于无访问保护；公开部署前需确定两人共享链接的访问与撤销方式。
- 验证空库 migration、备份恢复、应用与数据库重启恢复、HTTPS 及发布回滚。
- 当前全局数据库异常只返回统一错误，尚缺可定位异常的服务端日志；发布前补足日志且不输出凭证。
- 现有类型生成及契约测试不验证每个真实响应的全部 schema；发布候选阶段补接口响应一致性和跨设备验收。
- 搭配组合标识由应用与关联表同事务维护，唯一索引保证标识不重复；数据库未用触发器验证标识与关联集合完全一致。直接维护数据库须遵循此不变量，不把唯一索引误说成所有任意 SQL 写入都受完整语义保护。
