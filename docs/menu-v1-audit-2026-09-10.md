## 2. 真实数据与页面检查

- 当前菜单页可读取真实 API 数据；待完成与历史同屏，菜单记录带日期和餐次。
- 安排页默认晚餐，支持早餐、午餐、晚餐；选择已有菜名、创建新菜名、为每道菜选择库存耗材均已接通真实 API。
- 历史记录可展开查看实际用料；库存清单不混入消耗明细。
- 当前业务库仍有先前联调留下的 `demo-flow-2`、`demo-dish-*` 等菜品和菜单，影响日常浏览，但不代表菜单逻辑错误。

## 3. 本轮发现的缺口

### P1：安排入口的信息层级仍偏重

安排一餐弹窗同时展示常用搭配、就地新增菜名、完整菜品清单和每道菜的耗材编辑。它们都有效，但第一次安排一餐时会把“选菜 → 贴耗材 → 保存”这个主动作淹没。

已按建议保持业务和 API 不变，仅调整前端层级：

1. 默认先呈现日期、餐次、菜品选择和“新建菜品”。
2. 用户选中菜品后，再展开该菜的耗材区。
3. 常用搭配已收为“从常用搭配开始”的可展开次级入口，不再与首要操作同级。

### P1：联调数据目前会干扰浏览

历史区混有技术联调菜名，使用者无法判断哪些是自己真正安排过的菜单。当前业务库中的食材、菜品、菜单、搭配和消耗均是测试数据；用户后续直接提出“清空数据”时，统一按完整清理处理，不根据名称猜测保留范围。

当前不执行清理。后续收到明确的“清空数据”指令后，先备份再清空全部测试业务数据；不需要逐项识别或保留名称看似合理的记录。

### P2：前端确认请求绕开了生成的类型

`frontend/src/api.ts` 中 `BattleConfirm` 仍是 `any`，而 OpenAPI 已提供 `BattleConfirm` schema。应改用生成类型，让菜单确认请求在编译时受到契约约束。该修复不改变产品行为或 API。

### P2：历史查询目前一次性读取所有记录

前端为便于同屏排序读取全部菜单与消耗记录。个人厨房的 V1 规模可接受；当历史积累后，应改为后端分页和按日期窗口加载，避免为很久以前的记录重复请求。此项不阻塞当前体验。
