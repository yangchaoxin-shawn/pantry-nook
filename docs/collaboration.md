# Pantry Nook 协作流程

更新：2026-09-15。适用当前 ChatGPT Work / Codex 主负责人协作、开发与发布维护。

## 范围批准

用户用自然语言描述场景，agent 将其整理为问题、预期结果、改动范围、验收方式。
用户要求先看方案时先只读调查；收到批准后完成约定范围，不重复索要同一许可。
新增产品取舍或扩大范围时再确认；文档与实现矛盾时先识别，不擅自改业务来迎合代码。

新业务须说明产品含义、数据模型、API、状态流转、迁移及安全/公开访问影响。
普通缺陷若已有已确认规则，直接按该规则提出修复范围，不要求用户重复设计接口。

用户已授权后续协作按需使用子 agent。主负责人划分独立任务及文件范围，优先并行只读审查或互不重叠的工作，负责整合和最终验收；子 agent 的结论不代替主负责人的验证，也不扩展到部署、插件、定时任务或数据清理授权。

## ChatGPT Work / Codex 固定协作机制

| 角色 | 固定职责 |
|---|---|
| 主任务 | 冻结范围、安排工作、整合修改、处理审查发现、运行最终门禁并向用户交付 |
| 实现 agent | 只处理边界清楚、文件范围不冲突的实现；返回改动、验证与未覆盖范围 |
| 独立审查 agent | 只读检查业务规则、代码差异、部署配置或候选产物；不把“已通过”当证据 |
| 运行核验 agent | 使用最终构建产物、真实 API、浏览器或线上入口核对实际状态 |

小型文案和单文件低风险修复可由主任务独立完成。跨前后端、数据库、共享配置、部署和访问控制必须安排独立只读审查；部署同时安排部署前配置审查与部署后实际链路核验。主任务逐条处理审查发现，并亲自运行最终验证后才能过门禁。

## 一次迭代

新增能力先做有范围的调研，优先复用项目内已有能力、成熟开源组件或官方 SDK。结合官方文档核对维护状态、许可证、依赖体积、目标平台兼容性和数据处理方式，记录候选、选择理由与尚待验证的边界，再通过最小验证决定是否接入。不为调研广泛安装依赖，不把“有这个库”当作已完成业务、鉴权或多端验证；简单需求也不为复用强行引入复杂框架。视觉与交互先在独立设计稿中评审打磨，用户确认设计后再进入项目实现。

1. 读取状态、对应规格与代码，检查 Git 和实际运行环境。
2. 明确本次是业务变更、缺陷、视觉还是文档整理；选择必要的验收场景。
3. 在批准范围内实施。涉及业务时按规则/数据模型与 migration → 后端事务 → API 契约 → 定向测试 → 前端真实 API 的顺序推进。
4. 验证本次改动及受影响路径，按需要做差异审查。
5. 同步当前规格、状态、必要验证证据，并建立范围明确的 Git 提交。
6. 提交给用户验收；用户提出的新反馈先记录为问题，未批准的扩展不混入本轮。

## 验证分档

| 改动 | 必要验证 | 扩大条件 |
|---|---|---|
| 文档与协作入口 | 本地链接、事实一致、导入路径、Git 差异 | 文档含命令时对照脚本；本轮不运行写入命令 |
| 纯文案/视觉 | 对应页面与受影响尺寸/主题；修改 TSX 时做必要类型/lint 检查 | 共享组件或布局影响多个页面时扩大到相关页面 |
| 表单与局部交互 | 对应成功、空输入、失败恢复与边界；相关逻辑/API 测试 | 影响公共请求层、通用弹窗时覆盖所有直接调用者 |
| 模块业务/API | 模块真实 API 断言、契约与生成类型检查、相关浏览器闭环 | 改库存/数量/事务等共享逻辑时覆盖全部受影响模块 |
| migration | 独立库首次初始化、旧库升级、重复执行及恢复演练 | 涉及多模块历史或约束时扩大回归 |
| 发布候选版 | 后端及前端全量检查、真实浏览器、迁移与发布环境验证 | 进入发布阶段后单独授权部署 |

## 发布七道门禁

1. **G0 范围门**：记录用户批准的目标、真实域名/路径/端口、鉴权、数据口径和验收方式。
2. **G1 候选门**：核对分支、未提交改动、用户已确认的版本、`scripts/check-version.ps1`、环境参数和部署目标；不拿旧报告代替当前候选。
3. **G2 类生产门**：运行 `pwsh ./scripts/preflight-release.ps1`，用测试专用空库、Docker 后端和临时 Nginx 复现 `/pantry-nook/`、Basic Auth、SPA、静态资源和 API 代理。
4. **G3 独立审查门**：独立 agent 只读检查最终产物、Nginx 路径/API 重写、数据卷、目录权限、鉴权覆盖和回滚。
5. **G4 服务器变更门**：遵守部署 skill 的文档确认与连接许可；先摸查和备份，精确修改共享配置，检查差异及 `nginx -t` 后才重新加载。
6. **G5 线上核验门**：匿名入口、静态资源和 API 均被鉴权；登录后真实 CSS/JS/字体返回正确正文和 MIME；六个真实列表 API 返回 JSON；后端 `/health`、容器和浏览器控制台正常。只在已确认首次空库时检查空数据，普通升级核对 migration 与数据可读性。
7. **G6 记录门**：写明实际版本、验证结果、备份/回滚位置、故障与修复、未覆盖项；同步项目状态后再报告部署成功。

本地预检可清理的只有名称、端口和卷都带 release-preflight/test 标记的隔离环境。线上已有用户数据后，普通发布、回滚和重新构建都不得运行 seed/reset、清表、`down -v` 或删卷。若交付物必须带 Demo 或初始业务数据，先把环境归类为 disposable Demo 或明确导入/迁移，并单独写来源、备份、幂等和回滚。

状态码 200 不能单独证明页面可用。静态资源必须同时检查正文不是 HTML、哈希文件真实存在和 MIME 正确；API 必须使用真实接口，检查 JSON 结构，不能凭猜测的地址判断代理好坏。

范围由依赖与风险决定，不由改动行数决定。编译只证明语法可编译，不证明服务运行、接口可用或业务正确。
当前脚本粒度尚不支持所有单场景筛选：先选最小相关现有脚本，明确其中的跨模块覆盖；不要声称已有未实现的测试选择器。
执行命令及各脚本覆盖范围只在 [测试说明](../backend/TESTING.md) 维护。

## 用户验收环境

- 用户使用的本地页面和数据库在其验收期间保持稳定；不擅自刷新浏览器、结束服务或替换数据。
- 自动写入回归使用带测试标记的隔离服务，不连接业务端口 3000。
- UI 第一批已使用 `.worktrees/ui-foundation`、5200/3018 和独立测试数据库；启动、复用与进程校验见 [评审环境](ui-review-environment.md)。原 5173/3000 应用不跟随本批代码热更新。
- 独立的是代码、端口和数据库，仍共享本机 PostgreSQL 实例和 Python 运行环境；没有搭建容器、虚拟机或 Codex Actions。仅建立 worktree 不能隔离数据库。
- 本地演示数据替换是单独授权的数据操作，不作为普通测试的准备步骤。

## 常见反馈的验收场景

| 场景 | 应检查的结果 |
|---|---|
| 批量五行只填一行 | 忽略空白行；已开始但不完整的行提示补齐；取消冲突不丢输入 |
| 同名不同分类/单位 | 在当前流程弹窗选择；不可换算时填写最终量；不会写入两条同名在库记录 |
| 全部报废 | 从库存消失后，仍能在全局处理记录找到并安全撤销 |
| 保存菜单 | 每道菜有耗材；库存不变；草稿预计量未补齐时不得确认 |
| 核对实际用量 | 只编辑实际量；当前库存只读；合计不足时拦截 |
| 确认与撤销 | 重复提交不重复扣除；失败回滚；后续库存已变时拒绝不安全撤销 |
| 删除有引用的对象 | 解释引用与可行处理路径；不破坏搭配或历史 |
| 页面显示旧结果 | 检查代码版本、服务与 API 指向，区分旧实例、请求失败和渲染问题 |

以上是验收要求清单，不表示每条都已有自动化浏览器脚本。

## 状态与证据

状态分开记录：业务已确认、已实现、agent 已验证、用户已验收。
历史验证必须带来源/日期/版本；未运行写“本轮未运行”，不能引用旧计数冒充新结果。
用户反馈建议记录：问题 → 场景/预期 → 所属模块 → 修复提交 → 验证结果 → 用户验收。
[项目状态](project-status.md) 维护现阶段信息；复杂任务可增加执行计划，小改动不要求新增报告文件。

## 交付

日常交付：改动及原因、修改文件、实际验证和边界、剩余事项/用户测试路径。
纯文档不罗列大量“前后端未改”的空项目，也不跑无关测试。
模块冻结或发布需完整列出：修改/新增/删除文件，前后端实现，数据库/migration，OpenAPI，
视觉，真实 API，未完成，产品待确认，后端检查，typecheck/lint/build，桌面/移动浏览器，
控制台和 React runtime error；每项明确本轮结果或未验证。
agent 验证通过后标“待用户验收”，只有用户明确确认后才更新为通过。

## 机制使用

AGENTS.md 承载短规则；PRD 承载业务；状态表承载进度；历史报告只留证据。
Memory 仅辅助回忆，不能替代当前文件或实时核验。
Skills 按任务触发；独立审查与多 agent 按上述风险门槛重复使用。插件、定时任务和范围外外部写入仍按具体需要授权。
用随后 3～5 次迭代的重复解释、返工次数和验证耗时评估协作，未记录前不宣称效率提升。
