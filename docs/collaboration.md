# Pantry Nook 协作流程

更新：2026-09-17。按任务大小选择流程；不为简单改动增加完整报告和审批链。

## 范围与三种节奏

用户描述场景，负责人明确问题、预期结果、范围和验收方式。要求先看方案时先调查；批准后完成该范围，同一许可下的实现、修复、验证和文档收尾不重复询问。新的业务取舍、范围扩展、版本/tag、生产或数据操作仍按实际授权处理。

| 节奏 | 做法 | 交付 |
|---|---|---|
| 日常小改 | 对照已确认规则直接修复已批准问题，定向验证 | 简短结果、实际检查、本地 commit |
| 新能力/明显交互变化 | 先查现有系统和最大不确定点，评审必要设计，再完成业务闭环 | 可体验的真实模块、边界与用户验收路径 |
| 发布 | 冻结准确候选、完整类生产验证、独立审查、授权部署与线上核验 | 发布记录、回滚依据、准确版本及验证覆盖 |

每轮开工只需说明：本次用户路径、准确代码基线、复用与新增范围、最大不确定点及验证方法、完成标准。小任务可以一句话交代，不要求另建计划文件。

## 设计与可行性先对齐

新增能力先查看全部现有一级页面以及直接关联的表单、弹窗、反馈与空状态。区分共享设计规则与内容特色：主题、功能文字层级、按钮、图标、表单、弹窗和操作反馈沿用一套系统；照片组合、内容排版和专属插画可以创新。完整检查不等于重新设计所有旧模块，保留用户已认可的菜品展示等基线。

旧模块以准确版本的真实页面或截图为比较依据，不在设计稿中另写一套完整旧页面。新能力或尚未确定的交互先做最小设计评审，优先在隔离环境复用现有组件；已明确的小修复可直接改实际组件。设计稿只表达待确认的差异，不能变成另一套长期产品，也不能替代 API、数据和业务规格。

先验证可能推翻方案的风险，再铺开实现。平台相册、权限、文件来源、格式转换等能力，既要验证技术可行，也要验证用户能否以可接受的步骤完成。样本文件解析成功不代表手机相册能交付该文件；桌面模拟和自动化浏览器不能冒充真机验收。无法取得关键证据时，清楚列出未验证点及对方案的影响，不能只标注“后续测试”便把依赖它的方案视为已成立。

调研优先复用项目能力、成熟开源组件或官方 SDK；核对维护、许可证、体积、平台与数据处理边界，做最小实验后再接入。不为简单需求引入复杂框架，也不重复调研已确认且未变化的结论。

每次评审说明需要决定的差异；设计反复来回时先检查基线、目标和技术限制，不继续堆装饰。负责人在交给用户前走完进入、输入/选择、保存、查看和再次编辑，并检查相关空白、失败及恢复路径。用户负责产品判断，基础质量由 agent 先检查。

## 一次实施

1. 读取状态和对应规格，核对准确提交、工作区改动及服务/数据库指向。
2. 确定受影响路径和必要验收。业务变更先明确规则、数据模型、状态流转、迁移与访问影响。
3. 在批准范围内按规则/数据模型与 migration → 后端事务 → API 契约 → 定向测试 → 前端真实 API 推进。
4. 审查改动，处理发现，完成相应验证；不把单纯编译通过当成体验或业务通过。
5. 更新对应的唯一事实来源，按 [提交约定](git.md) 建立范围明确的本地提交。
6. 交付实际结果、未覆盖范围和必要用户验收路径；用户提出的新取舍不悄悄混入原范围。

## Claude Code / Codex 共同协作机制

| 角色 | 职责 |
|---|---|
| 主负责人 | 对齐方向和基线，划分范围，整合修改，处理发现，亲自运行最终门禁 |
| 实现 agent | 处理独立文件范围，返回修改、实际验证与未覆盖项 |
| 独立审查 agent | 按本阶段检查方案或实际差异，返回可定位证据；不把别人说的“通过”当证据 |
| 运行核验 agent | 按指定候选和环境核对真实产物、API、浏览器或线上链路 |

只把可独立且有价值的任务并行。任务交接要写清工作目录、准确提交、文件归属、阶段、验收与禁止操作；不得默认子 agent 位于正确 worktree。避免重叠编辑、重复跑同套测试或递归派生审查。

跨前后端、数据库、共享配置、部署和访问控制必须有独立只读审查；部署另含部署前配置审查与部署后实际链路核验。普通文案、小修复或事实同步由主负责人完成即可。方向审查在实施前解决取舍，代码审查在候选完成后检查实际问题；不要让审查扩展成另一轮无边界设计。

主负责人处理每项发现并运行最终必要门禁。独立证据可以复用；无新增风险时不要求每个 agent 重复全量验证。

## 验证分档

| 改动 | 必要验证 | 扩大条件 |
|---|---|---|
| 文档与协作入口 | 链接、事实一致、Git 差异；新增脚本检查实际行为 | 含操作命令时核对参数与失败路径，不实际执行生产写入 |
| 纯文案/视觉 | 对应页面与受影响尺寸；TSX 做必要类型/lint 检查 | 共享组件或布局影响多页时扩大到相关页面 |
| 表单与局部交互 | 成功、空输入、失败恢复、边界及相关逻辑/API | 公共请求层或通用弹窗影响所有直接调用者 |
| 模块业务/API | 真实 API 断言、契约/生成类型、浏览器闭环 | 库存/数量/事务等共享规则覆盖所有受影响模块 |
| migration | 独立库首次初始化、旧库升级、重复执行与恢复演练 | 多模块历史或约束变化扩大回归 |
| 发布候选 | 前后端全量检查、真实浏览器、迁移与类生产环境 | 部署单独取得实际授权后执行 |

范围由依赖和风险决定，不由行数或测试数量决定。只有新改动、失败或未解决的风险才扩大/重复检查；说明重复原因。现有脚本不能细分时，使用最小相关脚本并如实说明覆盖，不宣称已有不存在的筛选能力。命令入口统一见 [测试说明](../backend/TESTING.md)。

## 发布七道门禁

1. **G0 范围门**：确定目标、真实路径/端口、鉴权、数据保护及线上验证模式。默认不上传本地/test 数据；若完整公网上传验收需要临时写入，先明确取得该操作与清理范围授权。只读发布需明确记录未验证公网真实上传。
2. **G1 候选门**：核对准确 commit、干净工作区、用户确认的版本、`scripts/check-version.ps1`、环境参数与目标；旧报告不代替当前候选。
3. **G2 类生产门**：运行 `scripts/preflight-release.ps1`，以测试专用空库、Docker 后端和临时 Nginx 复现子路径、鉴权、静态资源、API 和完整媒体上传/读取。涉及升级时补带历史的迁移与恢复演练。
4. **G3 独立审查门**：检查最终制品、代理路径、鉴权覆盖、目录权限、持久卷、备份和回滚。固定执行脚本先做语法与离线失败路径检查；本地检查不代表服务器演练。
5. **G4 服务器变更门**：按部署 skill 与 [项目部署说明](../DEPLOY-SERVER.md) 执行。制品、工具、环境与镜像先准备并核对，再进入停写备份窗口。使用已审查的固定脚本与明确参数，不临时拼接多层 Shell/stdin 脚本；共享 Nginx 变更仅在授权范围内检查差异、语法后重载。
6. **G5 线上核验门**：检查匿名入口、资源/API/媒体鉴权，真实哈希 CSS/JS/字体正文与 MIME、真实列表 API JSON、Linux 权限、后端健康和浏览器。获准临时上传时再核验公网上传、GET/HEAD/Range、原图字节与取消后不可访问；只读模式将这些写入检查标为未执行。首次空库与普通升级采用不同数据断言，不能清空已有数据以通过检查。
7. **G6 记录门**：写明制品/版本、每项实际结果、备份与回滚位置、修复及未覆盖项，再更新状态。任何跳过项均不能包装为“全部门禁通过”。

类生产清理只允许作用于名称、端口和卷均带 test/release-preflight 标记的隔离环境。生产日常发布和回滚不 seed/reset、清表、`down -v` 或删卷。必须携带初始业务数据时走单独批准的版本化导入/迁移；disposable Demo 必须明确且使用专用库/卷。

HTTP 200 不能证明可用：静态资源需真实文件正文和正确 MIME，API 需准确接口及约定 JSON。备份、事务和数据持久性检查不能为提速省掉。

## 评审入口与跨会话交接

每轮只有一个标明版本和用途的当前评审入口，记录在 [项目状态](project-status.md)。旧设计端口是历史证据，不默认仍在运行。用户验收期间不擅自结束服务、热更新其目录、刷新页面或替换数据；隔离范围同时包括代码、端口和测试数据库，见 [评审环境](ui-review-environment.md)。

交接同时区分线上发布提交、包含后续维护的开发提交和用户正在看的入口。新任务创建返回或提示词写对不代表工作目录正确。创建后在目标工作区检查实际 HEAD、改动与部署祖先，并回传结果：

```powershell
pwsh ./scripts/check-handoff.ps1 -ExpectedRef <交接给定的准确开发提交> -DeployedRef <已核对的部署tag或提交>
```

默认要求准确相等与干净工作区；只有明确接续后续提交时才用 `-AllowDescendant`。不以 `-ExpectedRef HEAD` 自证正确。脚本只读，不修复；旧分支、分叉或用户改动先辨明来源，不覆盖或强制重置。用户已授权同步时可在确认安全后切换准确基线，再核验；不能只把新文档复制进旧代码就宣布同步。

交接索引只指向当前状态与规则，不复制全部上下文。新任务首次回复简述实际基线、范围和未解决事项，不重新启动已完成的调研或要求同一许可。已批准范围内的事实纠正和文档收尾直接完成。

## 状态与证据

- AGENTS.md：短而稳定的执行规则；PRD：当前业务规则。
- project-status.md：唯一当前进度、准确发布依据与下一步；CHATGPT_HANDOFF.md：读取与核验入口。
- 实现/运维文档：技术边界；历史报告：带日期与提交的证据，不能替代当前规格。
- 业务已确认、已实现、agent 已验证、用户已验收分别记录。未运行写明未运行；未经用户确认不标用户通过。

日常交付简短：结果与原因、实际验证、边界和下一步。模块冻结或发布按影响范围完整交代前后端、迁移/契约、视觉、真实 API/浏览器、未完成与待确认事项；不堆与任务无关的“未改”清单。

## 持续改进

用户已授权 agent 在协作中主动改进，而非等待逐项指出。发现重复返工、重复解释/审批、失效文档、测试重复、交接错误或工具摩擦时：

1. 分清是目标/规则不清、证据不足、工具缺陷还是执行遗漏，避免用增加步骤掩盖原因。
2. 在既有授权内实施最小有效改进，优先修正源头、复用工具、合并或删除重复规则；只在改变产品取舍、扩大范围或涉及受限操作时重新确认。
3. 验证改进本身，日常结果中简述关键变化；小改进不另建长报告，不启动自动化或外部服务。
4. 在随后相关迭代观察是否减少重复解释、设计返工、交接纠错与无理由的重复测试。有效则保留，无效则替换或撤回；没有记录不编造节省时长。

本轮从三处执行：设计与平台风险前置；准确代码交接校验；发布固定脚本与验证覆盖如实记录。随后三次相关迭代检查效果，不要求每轮填写新表。持续改进应让工作更顺畅，不能变成持续扩充检查清单。

Memory 只辅助回忆，不替代当前事实。Skills 按任务触发；多 agent 按上述边界反复使用。权限便利不等于产品、版本、生产、数据或用户配置无限授权。
