# 手记媒体运行与发布前门禁

本文件适用于新增媒体能力候选版；当前线上仍是 v1.1.0，尚未部署手记。

## 存储与运行

- Docker 通过 `MEDIA_ROOT=/data/media` 使用独立 `pantry-media-data` 卷，可由 `PANTRY_MEDIA_VOLUME_NAME` 固定名称覆盖。数据库卷与媒体卷均不随日常发布删除，不把照片写进镜像层或前端静态目录。
- 静态图片仅依赖锁定的 Pillow/pillow-heif；Docker 不再安装 FFmpeg/FFprobe 或 ExifTool。测试素材仍放 Git 忽略目录。
- 媒体只能从 `/pantry-nook/api/journal/media/...` 读取；Nginx 项目级 Basic Auth 覆盖原图、预览图和缩略图。不得额外 alias 媒体目录。
- Nginx 项目 API 上传请求限制 52 MiB、代理等待 180 秒；应用仍独立限制请求体与单个文件，不能仅依赖 Nginx。
- 清理工具默认仅预览，生产物理清理必须另行确定范围。软删除立即阻止 API 访问，不等同于已经从备份或磁盘物理清除。
- 清理工具只处理数据库登记的过期资源；文件转正后数据库提交失败、进程中断等情况可能留下未登记目录。当前不自动扫删这些文件，应停写后比对目录清单与数据库路径，人工核查并另行批准清理。普通发布不运行清理工具。

## 一致备份与恢复

旧发布说明中的数据库 dump 对媒体版本已经不充分。每次正式发布/数据恢复必须额外执行以下步骤并记录实际路径及校验值；不把数据库备份替代媒体备份：

1. 进入维护窗口，停止全部写入进程和媒体清理，等待正在处理的上传结束；仅停止前端页面不能阻止写入。备份期间保持后端停止，数据库可运行以执行 dump。
2. 使用本次唯一备份目录，同时保存 PostgreSQL 自定义格式 dump 与完整媒体目录归档。核对实际媒体卷名，不猜默认值，不搬运本地测试数据。
3. 记录数据库 dump、媒体归档 SHA256，以及每个原件的相对路径、大小、SHA256；保存对应 migration 版本和应用制品标识。不把原始照片、口令或备份提交 Git。
4. 恢复演练只用新建的隔离测试库与新媒体目录/卷。核对记录数、ready 资源是否齐全、每个原件校验值、旧记录兼容与历史文件保留、删除对象仍不能经 GET/HEAD/Range 获取。
5. 完成校验再恢复写入。生产恢复数据库时必须使用同一备份时点的媒体集合；普通应用代码回滚保留新增数据库表和媒体卷，不以清表、删卷或覆盖媒体实现回滚。

项目发布执行以 [DEPLOY-SERVER.md](../DEPLOY-SERVER.md) 为准：服务器 `.env` 固定 `PANTRY_MEDIA_VOLUME_NAME`，发布记录同时保存媒体卷名、媒体归档、逐文件清单及两个 SHA256。首个媒体版本即使旧容器没有媒体挂载，也先建立固定空卷并形成可验证的空卷备份，后续发布始终复用同一卷。

## 发布前必检

本轮只做本地实现和验证，不执行服务器步骤。未来发布除了原有类生产门禁，还需实际验证：

- 带历史的 12→14 增量迁移和空库启动，旧业务内容不变；不能只看 migration 登记表。
- 大于 1 MiB 的真实图片上传经过 Nginx 成功，MOV/MP4 上传应被拒绝，不误回 HTML；无 Content-Length 的超限请求仍被应用拒绝。
- 匿名上传/列表/所有媒体 GET、HEAD、Range 被拦截；登录后 MIME、字节内容、206 正确；删除后资源与条件请求均拒绝读取。
- 重启或重建应用容器后，PostgreSQL 与媒体卷内容一致且原件可读取。
- 发布后公网验证使用未绑定测试上传，验证完成立即经 API 取消并确认媒体返回 404；不创建假手记，也不清理既有线上记录。取消会立即阻止访问，但物理派生文件仍按受控清理流程处理，发布脚本不越权直接删卷内文件。
- 上述数据库＋媒体恢复演练通过；原发布脚本的通过不能自动代替这一检查。
- 版本号、tag 和部署仍需用户分别确认；移动设备系统选择器和图片浏览交互必须标明实际验收范围。
