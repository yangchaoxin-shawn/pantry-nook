# WorkBuddy V5 新能力确认提案

日期：2026-09-09。状态：**待用户确认，尚未实施**。

依据：现行 [PRD v0.3](PRD.md)、[设计交接](frontend-design-handoff.md)、`WB-V5-2026-09-09` / 设计系统 2.0。本文不修改 PRD；设计中的演示数据不导入业务库。建议确认后依次实现三餐与临期、统计、共享反馈。

## 一、早餐／午餐／晚餐：给作战分类，保持整次确认

**产品含义。** 每条今日作战属于早餐、午餐或晚餐；同一天同一餐可有多条作战，分别确认。菜品行显示其所属作战状态，不增加“单菜确认”。旧记录归入“未分类”，不根据时间或菜名猜测。新建时要求选餐次，旧客户端暂可不传；只有计划中的记录允许调整餐次。

**数据与 API。** `daily_battles` 新增可空 `meal_slot`，限定 `breakfast/lunch/dinner`。创建、修改和列表筛选接口支持该字段，详情返回字段；`null` 明确代表未分类。搭配方案仍是跨餐可复用的模板，不增加餐次字段。确认、取消、撤销继续沿用现有接口与事务。

**状态。** 保持 `planned → confirmed/cancelled`、`confirmed → planned/cancelled` 的撤销流程。一餐内所有未取消作战均确认才显示“全部确认”；没有作战显示“尚未安排”，不当成已完成。撤销确认后该餐状态重新计算，库存按原消耗恢复。

**迁移与安全。** 只增可空列和必要索引，旧值全部保留为 `null`；不合并、重排或覆盖历史。关闭三餐界面后旧作战仍可读取，已填餐次保留。该字段本身不扩大访问范围；将来共享仅按第四节所定义的权限展示。

**请确认 A：** 接受餐次可多条作战、旧数据未分类、整次作战确认的方案。

## 二、临期：用户填写日期，以家庭日历日判定

**产品含义。** 用户可为每条库存记录填写“到期日期”，留空显示“未填写”，不自动推断。日期仅用于提醒，不保证食材可食用，也不自动丢弃、扣库存或创建消耗。

固定按 `Asia/Shanghai` 日历日计算：今天至后天（差值 **0、1、2 天**）为临期；昨天及更早为已过期；晚于后天为正常。例：今天 9 月 9 日，9 月 9—11 日为临期，9 月 8 日为已过期。界面写“未来 2 个日历日内到期”，不写“48 小时内”。只对 `active` 库存提醒，过期单独计数。

**数据与 API。** `ingredients` 新增可空 DATE `expires_on`；新增/修改接口可提交或清除该字段。列表支持 `expiry=soon/expired/unknown` 筛选，响应可返回 `expiry_state`、`days_until_expiry`，由服务端按同一个日期计算。一次响应返回计算基准 `as_of_date`，避免手机与服务端时区不一致。

**状态。** 到期状态动态派生，和 `active/consumed/discarded` 分开。午夜或修改到期日期后重新计算；修改日期不调整数量，存在 planned 时也可改日期。用完或丢弃后退出提醒；撤销确认恢复 active 后重新纳入。

**迁移与安全。** 只增可空日期列，不回填旧日期。重复购买建议新建库存记录，各自填写日期；本轮不引入批次合并拆分。关闭提醒可保留日期，无须删列。日期默认仅在私有管理界面可见，共享反馈链接不暴露库存明细。

**请确认 B：** 接受到期日可空、临期含今天至后天、过期单列且不自动处理库存。

## 三、首页统计与周转：使用可解释的记录计数

**产品含义与计算口径。** 一条库存记录计为一条，不能宣称一种食材、一个实际采购批次或一份重量。建议调整原型卡片文案：

| 展示名称 | 计算定义 |
|---|---|
| 在库记录 | 当前 `active` 库存记录数，按 ID 计数；状态仍 active 的零数值记录也包含 |
| 临期／已过期 | 按第二节规则分别计数，不把未填日期视为正常或临期 |
| 本周动用库存 | 周一至今天、按作战日期筛选有效消耗，统计不同 `ingredient_id`；同条记录多次消耗只计一次 |
| 近 7 天日均动用记录 | 今天及此前 6 天，每天不同库存 ID 数的合计 ÷ 7；同一记录跨天分别计数 |
| 近 30 天平均用完天数 | 期间用完的记录，按 `ended_at` 的上海日期减 `purchase_date` 后求平均；缺采购日期或日期倒置的排除，并显示有效样本数 |
| 近 30 天丢弃记录占比 | 期间结清且当前为 discarded 的记录数 ÷ 期间结清且当前为 consumed 或 discarded 的记录数；显示分子／分母 |

“丢弃记录占比”不是重量废弃率；“平均用完天数”不是财务库存周转率。采购日期缺失时不使用录入时间冒充。不同单位不求和、不换算；分母或样本为零显示“暂无样本”，不显示 0% 或 0 天。

**数据与 API。** 建议新增只读 `GET /api/dashboard?date=YYYY-MM-DD`，返回以上聚合、时间范围、计算日期、时区与样本数。底层使用既有库存和消耗记录，不建可被前端写入的统计表；新增索引以实际查询验证为准。接口和页面统一使用上述字段含义，禁止替换成原型固定数字。

**状态。** 仅有效消耗参与计算，撤销后重新计算；取消与计划不算消耗。库存状态或采购日期被纠正后，历史区间统计也可能变化，因此这是“按当前有效记录重算”的统计，不是不可变的历史报表。今后若需要每次结清的永久历史，须单独批准事件模型。

**迁移与安全。** 除第二节日期列和可能的索引外，不回写业务数据、不补造历史；关闭页面与接口即可回退。统计仅限私有管理访问。公开反馈墙不携带库存数量、消费历史或这些统计。

**请确认 C：** 接受按库存记录计数、明确样本边界，并将“库存周转／废弃率”改为上述准确名称。

## 四、共享反馈：持有链接可留言，管理操作仍受保护

**产品含义。** 建议一个部署对应一个家庭。家人无须注册账号，持有有效随机分享链接即可查看反馈墙和留言；链接转发者也获得相同权限，因此不把昵称当成经过验证的身份。默认只共享反馈内容及明确关联的日期、餐次／菜名摘要，**不共享库存明细、数量、消耗历史、统计或管理页面**。

“已读”是家庭管理侧的全局处理标记，不代表某个家人读过。“采纳为待办”要产生真正能完成、取消、重新打开的待办：建议直接保存在反馈记录内，形成最小闭环，不接飞书或另建通用任务系统。已读和采纳相互独立，采纳不暗中标已读。

**数据模型。** 建议新增：

- `feedback`：正文（纯文本，上限 2000 字）、可空昵称与感受、可空作战关联、日期／餐次／菜名摘要快照、`read_at`、`adoption_status`、`todo_title`、`todo_status`、创建更新时间、`archived_at` 和版本号。感受限定很喜欢／有点困惑／想吐槽；不收集头像、设备指纹或联系方式。
- `feedback_events`：记录已读、采纳、撤回、完成、重开、归档等动作和时间，保留状态变化历史；区分分享权限与管理权限来源，不伪称真实操作者身份。
- `share_grants`：分享权限、令牌摘要、创建／到期／撤销时间。令牌由服务端使用密码学随机源产生，建议至少 256 bit；数据库不存明文。本文不生成令牌。默认有效期建议 30 天，可续发新链接，旧链接可立即撤销。

已关联作战删除时反馈保留摘要快照，关联设空；不因菜品更名改写旧反馈。只有现有管理侧授权才能更新状态，使用版本号检查并发修改，冲突返回 409。

**API 草案。** 下表均是待实现路径，不代表现在已可调用：

| 访问方 | 路径与用途 |
|---|---|
| 私有管理侧 | `POST /api/share-grants` 创建、`DELETE /api/share-grants/{id}` 撤销链接；首次返回明文链接，之后不可查询原令牌 |
| 链接持有人 | `POST /api/shared/session` 兑换有效令牌为有期限的访问会话 |
| 有效分享会话 | `GET/POST /api/shared/feedback` 查看、提交；只返回共享允许字段，分页并限制长度与请求频率 |
| 私有管理侧 | `GET /api/feedback` 含处理筛选；`PATCH /api/feedback/{id}` 修改已读、采纳、待办、归档状态 |

**状态流转。** 提交后：未读、未采纳、无待办。已读可恢复未读。采纳后待办为 open；open 可完成为 done 或取消为 cancelled，done/cancelled 可重开为 open。撤回采纳设为未采纳，同时取消待办，原待办标题和事件保留；再次采纳复用同一条待办，不重复创建。归档仅移出共享墙，管理侧仍可查看与恢复。访客不能修改他人反馈、处理状态或历史；如误发，由管理侧归档。

**迁移与回退。** 三张表初始为空，不导入原型反馈，不改变现有库存表。旧作战不自动建立反馈关系。关闭共享入口并撤销所有分享权限即可停止外部访问，已提交反馈及待办历史保留。撤销分享链接必须使已兑换会话同时失效；数据库回退不直接删除已经产生的数据。

**公开与管理安全边界。** 首选仍在现有私网／可信管理网络管理全部业务；分享入口只开放上述 shared 路径。当前没有账号保护的库存、确认、撤销等 API **不能随反馈墙一起暴露到互联网**。如后续必须在外网管理，需另行确认独立管理密钥或账号模型；分享令牌绝不能兼任管理密钥。

分享令牌放 URL fragment，页面兑换后移除地址中的令牌；不得出现在普通请求查询串、访问日志、分析服务或 Referer 中。会话用 HTTPS 下的 HttpOnly Cookie，写入校验来源和 CSRF，设置过期并逐请求检查撤销。正文按纯文本渲染、限流、限制请求体、不收附件；共享数据不进入公共缓存。无效、到期、撤销链接统一拒绝；泄漏时可撤销重发。反向代理、原有 API 的私网限制和撤销测试通过前，不公开部署。

**请确认 D：** 接受“持链接可看反馈与留言、私网管理已读／采纳”的权限边界，而不是设计稿中的“任何访客都能管理”；接受 30 天链接期限和反馈内真实待办。
