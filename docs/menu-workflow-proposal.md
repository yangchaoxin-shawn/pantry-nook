# 每餐菜单与库存闭环规格

> 历史记录（2026-09-11 归类）：保留当时方案与证据，正文可能含过期规则、数据和验证计数。当前业务以 [PRD](PRD.md) 为准，当前阶段见 [项目状态](project-status.md)；本文不授权重新执行数据或部署操作。

日期：2026-09-09。
状态：用户已明确批准执行；餐次、备餐关联、整餐核对与同屏历史已实现并完成真实接口联调。
验收记录见 [菜单闭环交付报告](menu-workflow-delivery.md)。本次批准不包含旧 V5 提案中的临期、统计、共享能力。

## 1. 已确定的产品含义

- 库存只展示现有食材，按碳水、蔬菜、蛋白质、水果、其他分组；清单只显示名称和当前余量，其他信息点开看。
- 菜单是一条每餐记录，例如“9月9日晚餐”，不是每天只能有一个菜单。
- 菜单记录包含日期、餐次、所选菜品及本次准备使用的库存食材，供备餐查看。
- 菜品库只保存名字；输入已有菜名可直接选择，没有时通过明确的“添加并选用”动作保存，避免把未完成输入自动存入库。
- 食材选择属于本次菜单中的这道菜，不是菜品库的固定配方。复用菜名不自动继承食材、用量或旧库存记录。
- 菜单可先保存为草稿，但每道菜必须先贴至少一种耗材；预计用量可以在准备时补全，不预扣库存。
- “确定”按一条菜单整体执行。核对页只显示已关联且已填写预计量的耗材：用户编辑实际用量，库存只读展示；系统按同一食材的整餐合计自动扣减并同步库存余量。
- 当前安排与历史同屏，上方安排新菜单及展示待完成菜单，下方展示已完成历史。
- 各区按用餐日期从新到旧排序，同日按餐次倒序，同餐次再按创建时间倒序；待完成记录不因日期过去而自动归档或确认。
- 完成归入历史是状态筛选，不移动或复制数据库记录。撤销后恢复库存、原菜单回到待完成区，原消耗以已撤销状态保留。
- 菜单详情可查看各菜品的实际用料。列表不堆叠消耗明细。
- 保留新增、查看、编辑与受历史保护的删除能力。有正式消耗历史的菜单不能直接删除；先撤销也保留历史引用。

## 2. 实施前差异与本次调整

| 要求 | 当前实现 | 本次调整 |
|---|---|---|
| 库存按大类分组 | 有分类筛选，全部列表未分组 | 全部视图按大类分组，保留名称和余量 |
| 日期与晚餐标识 | 有日期，同日允许多条记录，无餐次字段 | 新增餐次，界面用菜单称呼记录 |
| 安排与历史同屏 | 首页与消耗历史分开，主要按选定日期查看 | 菜单页包含待完成区和历史区 |
| 选菜时新增名字 | 菜品库支持新增，菜单选择器不能就地新增 | 添加并选用、重名时复用现有菜品 |
| 先选库存供备餐 | 仅在最终确认弹窗选库存 | 将每道菜本次所选库存持久化在菜单上 |
| 实际用量人工核对 | 已支持消耗原文、剩余原文和可选数字 | 确认页带入备餐食材，可调整，按实际量提交 |
| 确认、扣库存与撤销 | 已有事务与撤销快照 | 复用并扩展真实联调，保留原有事务保护 |
| 以菜品查询本次用料 | 消耗可关联具体菜品，但目前为可选 | 从备餐进入核对时保留菜品关联，详情展开查看 |

## 3. 数据模型方案

- 复用 `daily_battles` 作为菜单记录，前端不显示内部表名。
- 新增可空 `meal_slot` 字段：`breakfast / lunch / dinner`；新界面选择餐次，旧记录为空时显示“未分类”，不猜测旧记录是晚餐。
- 复用 `daily_battle_dishes` 保存本餐菜名快照，编辑菜品库不改历史。
- 新增 `daily_battle_preparations` 表：主键、本餐菜品行 ID、库存食材 ID、可空预计用量原文、显示顺序、创建与更新时间。同一菜品行不重复选择同条库存；同条库存可供多道菜使用。
- 备餐关联不预扣、不占用库存，不生成正式消耗。
- 最终用料仍保存在 `consumptions`，关联本餐菜品；保留库存变化前后快照用于可靠撤销。
- 确认页读取最新库存。若核对期间库存已变化，确认拒绝过期输入并要求刷新核对；不能仅依赖前端禁用按钮或覆盖新库存。

## 4. API 方案

沿用既有 `/api/dishes`、`/api/ingredients` 和 `/api/daily-battles`，不另起重复的菜单服务。

- 菜品新增继续用 `POST /api/dishes`；已有菜名直接选用，创建冲突后重新读取并让界面选中现有菜品，不重复建菜。
- 菜单创建和更新支持 `meal_slot` 及 `preparations`（菜品 ID、库存 ID、可空预计用量原文）。同一事务保存菜单、菜名快照和备餐关联。
- 创建和更新要求同时提交本餐全部菜品的 `preparations`；每道菜至少一项耗材，不能用空数组清空。预计用量允许为空，确认接口再校验预计用量完整。
- 菜单详情返回备餐食材及关联的菜品行 ID；列表按日期、状态、餐次分页查询。
- 确认沿用 `POST /api/daily-battles/{id}/confirm`，提交每道菜的实际用量和核对时的库存版本；前端据此生成每种耗材的整餐余量，后端在同一事务中复核并更新。
- 同一食材供多道菜使用时，分别保留实际用料归属；库存扣除与撤销按同一食材的消耗序列统一校验，不把同一整餐余量重复套到多条消耗上，也不跨单位推算。
- 取消、撤销和删除沿用既有接口与历史引用保护。

## 5. 状态流转

`待完成（planned） → 确定 → 已完成（confirmed） → 历史区`

- 保存、编辑备餐与取消均不扣库存。
- 确定在一个数据库事务中保存实际消耗、调整库存、更新菜单状态；任何一步失败全部回滚。
- 未使用的已贴耗材在核对页填写 `0`；保留菜品与耗材的核对记录，但不会改变该食材库存。
- 撤销已完成菜单：恢复确认前库存、消耗标记已撤销、菜单回到待完成区。存在后续库存变化时拒绝盲目恢复并显示原因。
- 取消的菜单保留，默认收进可筛选的历史区域，不混作“做过的菜”。
- 延续当前约束：存在未确认菜单时禁止直接新增库存或改库存量，仅允许修改库存元信息；本次不自行放宽用户原始规则。

## 6. 数据库迁移影响

- 新增一列及备餐关联表、约束和索引，使用增量 migration，不重置现有数据库。
- 旧菜单餐次为空；旧菜单无备餐关联；旧消耗与撤销快照保持不变。
- 不给旧记录补造预计用量，也不将测试数据转换为真实数据。
- 迁移前备份；已将这份旧数据备份恢复到独立测试库，验证迁移及重复执行均不改变原有记录。应用回退时保留新增字段和表中的数据，不以删表方式回退。

## 7. 安全与公开访问影响

- 本次不增加公开分享或访客写入；延续本地/可信网络使用边界。
- 现有服务没有账号权限保护，不能因这轮功能完善便视为可安全公开部署。
- 后端验证菜单状态、菜品归属、食材是否在库以及并发冲突，SQL 参数化。
- 业务数据存入 PostgreSQL，浏览器不以 localStorage 存储备餐计划或模拟多设备共享。

## 8. 验收场景

1. 库存分组只显示在库食材的名字与余量。
2. 输入“西红柿炒鸡蛋”：无同名时添加并选用，下次可直接点选。
3. 保存某日晚餐，选择西红柿、鸡蛋供这道菜使用；刷新或另一个浏览器访问后仍能看到备餐关联，库存不变。
4. 完成核对时核对每种已贴耗材的实际用量；确定后由系统按整餐合计扣减库存，菜单进入同屏历史。
5. 历史可展开查看菜名、实际食材和用量；新日期在上，旧日期在下。
6. 同一食材用于两道菜：实际用量归属可查，不重复扣减；撤销完整恢复。
7. 确认失败全部回滚；重复点击不会重复扣库存；核对期间库存变化时拒绝旧输入。
8. 撤销后菜单回到待完成区；存在后续变化时给出冲突而非覆盖库存。
9. 原有数据可正常读取；旧记录无餐次或备餐关联时可查看历史，新建菜单必须完成耗材关联。
10. 前后端契约、数据库事务回归、桌面与手机浏览器真实操作一起验证，再打磨 UI/UX。
