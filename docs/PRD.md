# Pantry Nook 当前 MVP 规格

更新：2026-09-17。本文件维护已确认的库存、菜品/搭配、餐安排与饭桌手记业务规则，不维护发布进度。
实现与验收状态见 [项目状态](project-status.md)，技术字段和请求详情见 [OpenAPI](../contracts/openapi.yaml)。

## 产品目标与边界

家里有什么 → 选择菜品并关联本餐耗材 → 保存备餐记录 → 做完核对实际用量 → 确认扣库存 → 查看历史或安全撤销。
家庭私有的响应式 Web，主入口为餐安排、库存、菜品与手记，常用搭配在菜品页。
前端仅展示用户完成动作所需的信息，不展示接口设置、数据库状态或“数量原文”等实现术语。

当前不做购入日期、保质期/临期提醒、营养/AI 菜谱、统计洞察、反馈墙、公开共享或账号权限。
餐安排按日期组织时间线，待完成与历史分区；保留历史日期筛选及原有操作。
菜品簿与餐安排时间线按稳定菜品 ID 展示同一个小人；菜品页和餐安排页使用已确认的厨房插画页头。小人只用于视觉识别，不新增菜品字段或选图步骤。
生产环境已采用服务器本机 Nginx、Docker 后端与 PostgreSQL；具体发布状态和数据保护边界以项目状态及部署文档为准。

## 库存 V1

- 大类：碳水、蔬菜、蛋白质、水果、汤料、其他。清单显示在库食材名称和当前量，其他信息点开查看。
- 汤料按家庭主要烹饪用途归类，例如石橄榄、虫草花、红枣、枸杞；直接食用的鲜枣仍可归水果，作为主菜的鲜菌菇仍归蔬菜。
- 新增/编辑的核心输入为名称、分类、数量、单位；位置和备注可选，不录入购入日期。
- 未填位置可保存；库存清单显示待补位置提醒、全库存待补计数与筛选，并可直接进入位置编辑。
- 库存数量按钮、上下键及聚焦后的滚轮每次增减 1；允许手动输入小数，保留现有六位精度。未聚焦时滚动页面不改变数量。
- 新入库、修改库存量及人工合并后的数量必须大于 0；未买到的食材留在餐安排待购买。已有零库存不自动删除或迁移。
- 库存所有编辑、菜品编辑、搭配编辑必须带记录版本。过期时拒绝保存并展示对方最新内容，保留当前输入；用户核对后可基于新版本继续编辑、再次保存。不自动覆盖或自动重试。
- 当前库存字段统一为 stock_text、stock_value、stock_unit；stock_text 保留用户输入/确认的数量文本，数值与单位用于计算。
- 数量不变时也可修改单位或其他属性；前端在数量或单位改变时成组提交三个 stock_* 字段，含义必须一致。后端拒绝只有部分 stock_* 字段或原文与数值不一致的请求；未改数量保留原文。
- 不再维护购入数量与当前库存两套字段，也不保留旧 consume/discard 兼容 API。
- 后端生命周期状态和历史库存快照用于事务及恢复，不作为日常库存详情内容。
- 单个记录只显示一个录入项；批量先选本批大类，填写的项目使用该类别。
- 完全未填写的行忽略；已开始填写的行需完整；至少一项才提交，整批原子入库。
- API 单个/批量入库共用一个服务；不因 API 共用而让单个入口显示多行。
- 录入时根据所选大类优先展示常用单位；类别只影响推荐顺序，不限制真实单位。批量录入可选本批默认单位，每项仍可单独修改；切换类别不得覆盖用户已填写的单位。

### 日常用掉

- 水果零食、牛奶等不属于早餐/午餐/晚餐的正常食用或使用，从食材详情选择“用掉了”；只填写本次用掉数量，不要求餐次、时段、人物或原因。
- 数量默认留空，单位沿用当前库存；可选择一半或全部用完，并在确认前看到预计余量。数量必须大于零且不超过最新库存。
- 日常用掉在短事务内校验库存版本、扣减库存并写独立记录；失败全部回滚。同一操作标识重试不重复扣减，网络结果不明时可用原操作标识核验结果。
- 全部用完后食材退出当前库存清单，但记录仍可从“消耗与处理记录”找到。撤销只补回本次用量，保留后续补货、库存调整和盘点结果；同名食材已经重新入库时先核对合并，不能产生第二条同名在库记录。
- 日常用掉不关联或修改餐安排。已有待完成菜单继续保留并在核对时读取最新余量；已经在餐安排确认中扣除的用量不重复记录。
- 只知道当前剩余量而不知道本次用量时，使用库存编辑校准；库存差额不自动虚构为一次日常食用记录。
- “消耗与处理记录”在同一页面分为“日常用掉”和“变质 / 损坏”两个页签，不提供再次混合的“全部”视图。每个页签独立显示仍可撤销、已经撤销、数量和空状态；默认打开日常用掉，返回页面保留上次选择，网址参数支持刷新后回到当前页签。
- 两类记录由服务端按 `kind=used|waste` 分开查询，避免记录超过单页上限后再由前端筛选造成遗漏；原有 `reason` 精细筛选继续保留。

### 同名与单位冲突

| 情况 | 处理 |
|---|---|
| 同名、同分类、同单位 | 累加到原有库存 |
| 同名、分类不同 | 当前流程弹窗选择最终类别 |
| 单位不同且能换算 | 弹窗选择最终单位，按既有规则换算后累加 |
| 单位不能换算 | 选择最终单位，人工填写合并后的实际库存，不猜换算比例 |
| 同一批重复填写同名 | 提示整理成一项，不能重复入库 |

在库名称按去首尾空格、大小写不敏感判同；每个同名在库食材只保留一条。
已支持质量单位 g/kg/斤、体积单位 ml/L 内的换算；跨量纲不换算。
用户选择前不落库；取消处理保留录入内容；失败不部分写入。
不要把上述同名范围扩大为“所有历史食材都必须同一条 ID”；历史记录须保留引用。

### 变质/损坏与安全撤销

- 入口为“处理变质/损坏”，支持全部或部分数量；原因是变质、损坏、其他，可写备注。
- 报废量大于 0，不超过库存；单位使用当前库存单位。
- 事务内写库存处理记录并调整库存。全部报废后不出现在当前库存清单。
- 库存页提供全局处理记录入口；详情可另有快捷入口。食材消失后仍能找到处理记录。
- 全局处理记录标明“库存 / 变质 / 损坏记录”并提供返回库存；返回保留原搜索、筛选及滚动位置。
- 报废撤销加回该次报废量并保留已撤销记录；保留后续补货、消耗和盘点结果，不覆盖为旧库存总量。确认校验最新版本，已经撤销不能再次加回。
- 全部报废或耗尽后，如已经重新录入另一条同名在库食材，撤销先弹窗核对合并；整餐撤销仍要求旧库存无后续变更。保留现有在库 ID 和属性，旧 ID 只保留历史，不能制造第二条同名在库记录。
- 合并可选择现有或原单位；支持的换算由后端计算，不可换算时手动填写最终数量。预览不占库存，确认校验来源、目标与菜单版本；冲突保留本次输入并要求重新核对。
- 合并恢复、反转原记录、写审计在同一事务中完成；整餐任一项失败全部回滚。历史显示合并去向，同一来源只恢复一次。
- 日常用掉、报废记录和菜单消耗保持语义区分；库存清单不堆叠这些明细。

## 菜品与搭配 V1

- 菜品只保存名字，支持新增、查看、编辑、复用和受引用保护的删除。
- 菜品以连续手写菜品簿展示，按菜名长度自然排布；编辑与删除始终可达，手机按钮区域按 6:4 分配。常用搭配标明所属菜品页，返回恢复原搜索及滚动位置。
- 菜品小人由稳定菜品 ID 决定；同一菜品在菜品簿和餐安排时间线保持一致，不随改名、刷新或页面切换随机变化，也不要求用户手动选择。
- 菜名去首尾空格，在有效菜品中唯一。安排菜单时可明确新增并选用，已有菜名直接选择。
- 菜品不保存固定耗材和配方用量；每次选用都针对本餐关联库存。
- 搭配是可复用菜品组合，支持增删改查；不关联库存、不改变库存。
- 相同菜品集合只能保存为一个搭配，菜品选择顺序不构成新搭配；创建或编辑冲突时引导使用已有搭配。有名称的搭配名称同样唯一。
- 从搭配开始安排菜单时复制菜品与菜名快照；之后编辑菜名/模板不改已有菜单快照。
- 菜品仍被搭配引用时不能删除，应展示引用与处理路径。
- 菜品被待完成菜单引用时同样不能删除，应引导先调整对应餐安排；已完成或已取消菜单继续依靠菜名快照保留历史。
- 保存搭配引用与删除菜品并发时只能成功一种操作，不能产生引用已删除菜品的新搭配。
- 未被搭配引用的菜品可软删除；历史菜单保留快照，不等于删掉历史。
- 搭配删除只影响模板本身，不删除已复制的菜单。

## 菜单 V1

### 选择与保存

- 一条记录对应一餐，包含用餐日期、早餐/午餐/晚餐和菜品；同一日期和餐次只能有一条记录。要调整内容时编辑这条记录，不新建第二条。
- 每道菜保存前至少关联一种库存耗材或待购买食材；相同食材可用于多道菜，同一道菜不重复关联同一种耗材。
- 每道菜在新增、替换或补购后修改库存关联时，可按库存大类筛选当前可选食材并看到各类数量；已关联项保持可见，筛选不改变已保存的关联。
- 待购买食材只属于本餐，保存名称和预计量，不伪装成零库存记录。补货后，仅当本次提交名称与待购名称精确同名（忽略首尾空格和大小写）、有效同名库存唯一、这餐仍为待完成、预计量可按已支持单位安全换算且不会造成同一道菜重复关联时，默认关联到真实库存；菜单仍待完成时，不满足其他条件的项目保留待购并进入人工修改，同餐其他安全项可以先完成关联。若补货期间菜单已经确认或取消，不再写关联，直接回到只读核对并说明最新状态。
- 当前草稿允许稍后补预计用量；未补齐不得确认。此规则承接此前菜单规格和 9 月 10 日审计，本轮不改变保存条件。
- 库存耗材的预计量非空时必须是数字或简单分数，可在末尾带当前单位；后端保存当时的库存单位快照。待购买食材没有确定库存单位，预计量仍保留用户填写文本。
- 菜单保存/编辑不预扣库存，不创建消耗，也不把耗材当作配方。
- 点击“核对用料”只读取最新库存，不锁定、不预占、不扣减。菜单预计量超过库存时保留计划并明确提示缺口。
- 编辑菜单首开读取最新菜单和库存，打开期间更新库存；保存前校验最新菜单版本。若并发编辑改变了旧单位快照，支持的换算先展示并等待确认，不可换算则保留输入并要求按当前单位重填。
- 数量输入随库存带上单位，避免要求用户重复理解后台字段。
- 菜单保存后库存单位若改变，核对时按已支持的同量纲单位自动换算并明确提示；不能换算时要求回到菜单重新填写，不能静默沿用数值。
- 复用历史菜单仅复用菜名；不自动把旧库存 ID 或旧实际量当成本次耗材。

### 核对与确认

- 以本餐已选择的菜品、耗材和预计量开始核对；预计量未完整时先补齐。待购买食材须先补货；菜单仍待完成时，满足安全匹配条件便默认关联，否则先人工选定真实库存。补货期间菜单已经确认或取消时转为只读核对。
- 每项只允许编辑实际用量，当前库存只读；未用的耗材可填写 0。
- 核对中的补货在同一餐流程内完成：已有库存补量后重新读取并返回核对；待购项符合上述安全条件时默认保存关联并直接回到原餐核对，同时提供“修改关联”。菜单仍待完成时，名称不一致、同名候选不唯一、单位不可识别或不可换算、原关联失效等情况进入人工修改，不猜测关联；菜单已变为确认或取消时直接回只读核对并说明最新状态，不进入编辑。
- 补货、取消补货、关联编辑及重读保留本餐仍对应同一菜品行与库存 ID 的实际用量；换单位时要求重新核对，不把旧数字套用新单位。
- 入库成功后的读取、自动关联保存或人工关联失败只重试对应步骤，不再次提交补货；入库结果未知时显示本次实际提交的食材供核对，只读重试也不自动重复入库。
- 页面不要求填写“做完还剩多少”或额外“扣减数值”。
- 同食材跨菜品合计扣除，保留各菜品用量归属；超库存或无效量不能确认。
- 前端只提交各菜品的实际用量和版本；后端计算整餐扣减，校验状态、归属、版本及业务约束，并在一个事务写消耗、调库存、标记已完成。
- 确认失败全部回滚；重复确认不重复扣减；不覆盖过期库存版本。
- 编辑已保存菜单必须提交菜单版本；省略版本同样拒绝，不能借此绕过并发保护。

### 状态、历史与删除

| 动作 | 状态/展示 | 库存 |
|---|---|---|
| 保存 | 待完成 planned，留在上方 | 不变 |
| 开始核对 | 仍为待完成，读取最新库存与本餐实际用量 | 不变 |
| 确认 | 已完成 confirmed，进入下方历史 | 按实际量扣除 |
| 取消 | 已取消 cancelled，保留历史 | 不变 |
| 恢复已取消菜单 | 原记录回到待完成 planned，日期、餐次、菜品和历史不变 | 不变 |
| 撤销确认 | 回到待完成；原消耗标为已撤销 | 安全校验通过后恢复 |

历史归档是状态筛选，不搬表、不复制业务记录。日期过去不会自动完成或取消。
已取消菜单需要继续安排时恢复原记录，不创建同日期、同餐次的第二条菜单；恢复必须校验菜单版本。
各区按用餐日期倒序，同日餐次倒序，同餐次按创建时间倒序。
历史可展开查看用料；有正式消耗历史的菜单不能直接删除，撤销也不抹去历史引用。
撤销合并到新库存后，本餐受影响耗材关联新 ID 并清空预计量，引导重新填写核对；其他菜单不自动修改。没有同名新库存时仍恢复原记录。
整餐撤销遇到后续相关库存变化时拒绝不安全恢复；报废撤销按独立报废量补回当前库存。

## 饭桌手记

- 独立页面按月份和日期倒序展示做饭照片记录；每篇 1–9 张照片、日期和可选文字，初次默认第一张为封面，可直接点击缩略图切换。支持相册多选、拖入、逐张重试、大图浏览、编辑照片/封面/日期/文字及确认后删除。
- 保留系统实际收到的原图片文件，另存缩略图和展示图；不承诺恢复操作系统或分享工具已经丢失的内容。原件和派生图片均属私有资源。
- 全平台统一静态照片：支持 JPEG（含 MPO 主图）、PNG、WebP、HEIC/HEIF。iOS/iPad 相册交付的图片直接保存；安卓内嵌动态的图片保留原文件，但只生成静态预览。不接受独立视频，不提供实况识别、配对、补传、动态提取、转码或播放。旧实况记录按静态照片读取和编辑，历史视频行与磁盘文件不因功能移除而清理。
- 记录不影响库存、菜单或消耗；本轮不关联餐安排，不增加公开分享、任意视频发布或 ZIP 导入。
- 上传重试与记录发布分别保持幂等；只允许就绪资源发布，同一上传不得并发绑定两篇记录。编辑必须校验版本，删除后相关图片和视频不可继续读取。
- 新增与编辑共用整理面板；右上角 × 移除草稿照片，可在 8 秒内撤销；替换新图就绪前保留旧图。移除封面后必须重新选择，零照片不得保存。取消系统选图不关闭编辑面板。
- 超过 9 张先挑选、确认后才上传，默认不选且不静默截断。选择和拖入共用格式检查，拒绝文档、伪装图片和任意视频。
- 1—9 张按数量与横竖比例展开不同排版，封面先展示，其余相对顺序不变；所有照片在手机也可见。图片编辑原子保存且保持幂等，版本冲突不得覆盖另一设备。
- 数据模型、接口和资源限制见[本轮实现约定](photo-journal-implementation.md)；自动化通过不代表当前版本手机相册选择器已经通过真机验收。

## 拍小票入库（OCR）

- 库存页提供"拍小票入库"入口：上传或拖入一张购物小票照片，本地 OCR 识别后给出可编辑草稿，人工核对确认后经既有批量入库写入；识别内容永远是草稿，没有人工确认不产生任何库存变化。
- 识别服务为独立侧车（`ocr/` 目录，PP-OCRv6 本地自部署），无需密钥、图片不出本机；backend 的 `/api/ocr/receipts` 只做转发和草稿解析，不保存图片。侧车不可用返回 503 并提示启动识别服务。
- 草稿每行含识别的品名、数量、单位和参考金额；金额仅用于与纸质小票核对，不写入业务字段。识别不出数量或单位的行标记待补，粘连无法拆分的数字保留在名称里由用户修正，解析拿不准时整行保留而不是悄悄丢弃。
- 草稿每行自动带出分类建议：先按在库食材名称匹配（用户保存过的食材即成为匹配库），再按内置常见食材词表兜底；匹配不到显示待分类，由用户手选，改过的分类随食材入库供下次自动带出。置信度偏低的行标记"识别不确定"，被解析跳过的行折叠展示可展开查看。
- 草稿可删除不需要的行；确认后预填现有批量录入表单并携带每行分类，分类、位置、数量与单位在彼处仍可修改，保存走同名冲突选择、单位换算与整批事务等全部既有规则。
- 单张小票不超过批量入库上限 30 项，超出部分提示稍后手动补录；单图上限 15MB。本轮只支持购物小票，不做菜谱截图、包装识别、历史记录或多张小票合并。

## 跨模块约束

- 待完成菜单和核对页面均不锁定、预占或扣减库存。入库、改库存量和报废可正常进行；只有最终确认以短事务串行校验并扣减。
- 两人使用同一套数据，不设置角色。核对窗口打开时读取最新数据，前台每 3 秒检查一次，回到页面及提交前重新读取；库存变化保留实际用量并提示重新核对。
- 页面读取失败与真实空数据必须分开展示；错误态提供重新读取，不把断网解释成“没有食材”。
- 提交前发现变化，本次不写入；事务内仍校验菜单和食材版本。对方已经确认/取消时停止提交；库存不足、食材不在库或待购买食材尚未关联库存时拒绝确认。网络结果未知只读取核验，不自动重发。
- 修改 stock_* 或不可换算单位的人工合并量必须携带 expected_updated_at；过期返回 409，不能覆盖另一人的更新。同单位/可换算补货在事务中按最新库存累加。
- 撤销确认采取保守版本保护：相关食材确认后只要发生后续更新就拒绝自动恢复，包括换单位、同量覆盖及后续操作再撤销；不猜测历史抵消。需要时在库存入口核对调整。
- PostgreSQL 持久化；SQL 用户值参数化，后端事务和版本校验不可由前端替代。
- 旧记录可读取，但不虚构旧餐次、耗材或预计量；当前库存 API 使用统一命名。
- 有数据的数据库使用备份与增量 migration，不能用重置替代升级。
